# 알려진 이슈 — 처리 기록

리팩토링 중에 발견한 원본의 잠복 버그들. 리팩토링 단계에서는 "동작 보존" 원칙에 따라
전부 그대로 두고 여기에 기록해 두었다가, 리팩토링이 끝난 뒤 일괄 처리했다.

**모든 항목 해결됨.** 아래는 무엇을 왜 그렇게 고쳤는지에 대한 기록이다.

## 1. hp ±1/±2 무효 구문 16곳 → 실제 효과 부여 (해결)

### 배경

리팩토링 전 `defineShims()`는 `S.hp`에 setter를 걸어 legacy 대사 데이터를 새 상태에
연결했다. 그 setter는 **변화량의 절댓값이 3 이상일 때만** 상처를 움직였다.

```js
var cur = Math.max(0, (MAXHP - this.wounds)) * 4;   // 0 wounds -> 16
var d = v - cur;
if (d <= -3)      this.wounds = Math.min(MAXHP, this.wounds + 1);   // 상처 +1
else if (d >= 3)  this.wounds = Math.max(0, this.wounds - 1);       // 상처 -1
// |d| < 3 이면 아무 일도 일어나지 않는다
```

따라서 `S.hp+=1`, `S.hp+=2`, `S.hp-=2`는 **호출되어도 아무 효과가 없었다.** 결과
텍스트는 `(목숨 회복)` 또는 `(작은 상처)`를 약속하는데 실제로는 상태가 변하지 않아,
**게임이 플레이어에게 거짓말을 하고 있었다.**

### 처리

16곳 모두 실제 효과를 부여했다. 텍스트가 약속하는 대로 동작한다.

- `(목숨 회복)` 9곳 → `if(S.wounds>0)S.wounds--;`
- `(작은 상처)` 7곳 → `if(S.wounds<MAXHP)S.wounds++;`

원본(`8bc002e`)의 `STORIES` 원문에서 다시 생성하는 방식으로 적용해, 삭제됐던 구문의
위치를 추측하지 않고 정확히 복원했다. 한국어 문자열은 471런 전부 그대로다.

### 밸런스 영향

`MAXHP`가 4뿐이라 난이도가 오른다. 다만 회복 9곳이 피해 7곳보다 많아 일방적으로
어려워지지는 않는다. 회복은 우호적 분기에, 피해는 적대적 분기에 몰려 있으므로
**협력적으로 풀면 더 유리하고 공격적으로 굴면 더 불리해진다** — 게임 주제와 맞는
방향이다.

너무 어렵다고 판단되면 이 커밋만 되돌리면 된다. 다른 변경과 섞여 있지 않다.

## 2. 날짜에 따라 변해야 할 NPC 소개문이 고정돼 있던 문제 → 게터로 전환 (해결)

`STORIES`의 intro는 두 가지 방식으로 날짜에 반응하도록 작성돼 있었다.

```js
intro:"…" + moodTail()          // 4곳 — 날이 갈수록 어두운 한 줄을 덧붙임
intro:S.day<=3 ? "…" : "…"      // 3곳 — 3일차 전후로 완전히 다른 문장
```

그런데 둘 다 **객체 리터럴이 만들어질 때 딱 한 번 평가되는 표현식**이었다. 그 시점의
`S.day`는 항상 `1`이므로 `moodTail()`은 늘 `""`를 반환했고, 삼항은 항상 앞 분기만
골랐다. **총 7곳의 날짜별 대체 문장이 게임에서 한 번도 보이지 않았다.**

### 처리

intro 8곳 전부를 게터로 바꿨다.

```js
get intro(){ return "…" + moodTail(); }
```

호출부(`startBattle`의 `st.intro`)는 그대로 두어도 대화를 시작할 때마다 평가된다.
이제 날이 갈수록 NPC 소개문이 실제로 어두워진다 — 원래 의도대로다.

새로 노출되는 문장은 전부 원본에 이미 있던 것이고, 새로 쓴 한국어는 없다.

## 3. `sendPrompt()` 미정의 → 가드 추가 (해결)

엔딩 화면의 두 번째 버튼(`이런 곳을 어떻게 바꿀 수 있을까?`)이 호출하는 `sendPrompt()`는
프로젝트 어디에도 정의돼 있지 않았다. 원본 `Glorya.html`에서도 **호출부 한 곳에만
등장**하고 선언이 없다. 다른 앱 안에 임베드되어 호스트가 제공하던 함수로 보인다.

리팩토링이 만든 문제가 아니라 처음부터 있던 버그이며, 누르면
`ReferenceError: sendPrompt is not defined`가 났다.

### 처리

호스트가 있으면 쓰고 없으면 조용히 넘어가도록 가드를 넣었다.

```js
if(typeof window.sendPrompt!=='function')return;
window.sendPrompt(...);
```

단독 실행 시 그 버튼은 아무 일도 하지 않는다(에러는 안 난다). 나중에 다시 임베드하면
코드 수정 없이 바로 동작한다. 프롬프트 문자열은 원본 그대로 두었다.

**남은 판단:** 단독 배포에서 이 버튼을 계속 노출할지는 결정이 필요하다. 지금은
"눌러도 반응 없는 버튼"이라 제거하거나 다른 동작으로 대체하는 편이 나을 수 있다.
UI 텍스트 변경이 필요해서 손대지 않았다.

## 참고 — 고치지 않은 사소한 차이

### `S.hunger-=24` 반올림

`S.food=Math.max(0,S.food-3)` 2곳(`가진 걸 내주고 사과한다`, `가진 걸 내주고 물러선다`)을
`S.hunger-=24`로 옮겼다. shim의 정확한 동작은
`S.hunger -= Math.min(24, Math.round(S.hunger/8)*8)`이었다.

차이는 `S.hunger`가 17~19인 구간뿐이며 결과가 0 대신 1~3이 된다. 100점 척도에서 최대
3점, 굶주림 직전 구간에서만 발생한다. 정확히 보존하면 shim의 반올림 왕복 부작용을
그대로 옮겨오게 되어 가독성을 택했다.
